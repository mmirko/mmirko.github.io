      1 # BMStack
      2 
      3 bmstack is part of BondMachine project. Within the project It is used to create stacks and queues distributed among several BondMachine cores. due to its generality it can also be used as standalone tool to produce HDL shared stacks and queues to be used in other projects.
      4 The HDL code is build using golang templates that creates the code starting from the following data structure. The comments describe the meaning of each field.
      5 
      6 ```go
      7 type Push struct {
      8   Agent string // The name of the agent that is pushing
      9   Tick  uint64 // The tick at which the push occurs
     10   Value string // The value that is pushed
     11 }
     12 
     13 type Pop struct {
     14   Agent string // The name of the agent that is popping
     15   Tick  uint64 // The tick at which the pop occurs
     16 }
     17 
     18 type TestBenchData struct {
     19   Pops         []Pop    // List of pops
     20   Pushes       []Push   // List of pushes
     21   TestSequence []string // Pushes and pops in order
     22 }
     23 
     24 type BmStack struct {
     25   ModuleName string   // The name of the module
     26   DataSize   int      // The size of the data bus
     27   Depth      int      // The depth of the stack
     28   Senders    []string // The names of the agents that can send data to the stack
     29   Receivers  []string // The names of the agents that can receive data from the stack
     30   MemType    string   // "LIFO" for a stack or "FIFO" for a queue
     31   funcMap    template.FuncMap
     32 
     33   // TestBench data
     34   TestBenchData
     35 }
     36 ```
     37 
     38 ## Usage
     39 
     40 ### Usage: API 
     41 
     42 The library can be used in two ways.
     43 The first one is from a go program. After creating a BmStack structure, the user can call the WriteHDL function to produce the HDL code.
     44 An example on how the library can be used this way can be seen in the go test file (bmstack_test.go).
     45 
     46 ```go
     47 func TestWriteHDL(t *testing.T) {
     48   // Create a new stack with 4 agents
     49   stack := BmStack{
     50     ModuleName: "test",
     51     DataSize:   32,
     52     Depth:      8,
     53     Senders:    []string{"sender1", "sender2"},
     54     Receivers:  []string{"receiver1", "receiver2"},
     55     MemType:    "LIFO"
     56   }
     57 
     58   // write the HDL code
     59   stack.WriteHDL()
     60 ```
     61 
     62 The second part of the struct can be filled with test data. These data are used to produce a test bench for the stack. Using the test bench the user can verify the correctness of the stack. The test bench is produced by calling the WriteTestBench function.
     63 
     64 ```go
     65 func TestWriteTestBench(t *testing.T) {
     66   stack := BmStack{
     67   // ...
     68     s.Pushes = []Push{
     69       Push{"sender1", 200, "32'd1"},
     70     }
     71     s.Pops = []Pop{
     72       Pop{"receiver1", 60},
     73     }
     74   }
     75   // write the test bench
     76   stack.WriteTestBench()
     77 }
     78 ```
     79 
     80 The two functions (WriteHDL and WriteTestBench) return a string that contains the HDL code or an error if something went wrong (string, error).
     81 The provided go test file (bmstack_test.go) shows how the library can be used in this way. When invoked (go test), it produces the two files (bmstack.v and bmstack_tb.v).
     82 This kind of usage is useful when the user needs to create a stack or a queue in HDL and then use it in a bigger project like it is done in the BondMachine project.
     83 
     84 ### Usage: CLI
     85 
     86 The library also came with a companion CLI executable called bmstack that provides the basic interface to the library. This is the second Possible way to use it.
     87 With the -h flag the user can see the available options and their meaning.
     88 
     89 ```bash
     90 $ bmstack -h
     91 Usage of bmstack:
     92   -d    Verbose
     93   -data-width int
     94         Width of the data bus (default 32)
     95   -depth int
     96         Depth of the stack/queue (default 8)
     97   -hdl-file string
     98         Name of the file to write the HDL to (empty string to disable) (default "stack.v")
     99   -memory-type string
    100         Memory type, either stack or queue (default "queue")
    101   -random-stimulus int
    102         Generate random stimulus including N pushes and pops for every agent (0 to disable)
    103   -receivers string
    104         Comma separated list of names of signal tags that will receive data from the stack/queue
    105   -senders string
    106         Comma separated list of names of signal tags that will send data to the stack/queue
    107   -sim-length int
    108         Length of the simulation in clock cycles (default 1000)
    109   -stimulus-file string
    110         Name of the JSON file to load the stimulus from (empty string to disable)
    111   -tb-file string
    112         Name of the file to write the testbench to (empty string to disable)
    113   -v    Verbose
    114 ```

    116 ## Examples
    117 
    118 Within the BondMachine project, the library is used to create stacks and queues in HDL whenever needed. Some example of this are:
    119 
    120 - The queue used by the thread manager in the CP cores to store the CP threads state
    121 - The stack used to store the return addresses in the call instruction
    122 - The queue used to get data for the keyboard
    123 
    124 To further see how the library is used in the BondMachine project, please refer to the BondMachine examples directory that contains many examples of BondMachines using stacks and queues. Instead, here we provide a simple example of how to use the library as standalone tool.
    125 
    126 ### Example: API
    127 
    128 The provided go test file (bmstack_test.go) shows how the library can be used in this way. When invoked (go test), it produces the two files (bmstack.v and bmstack_tb.v).
    129 
    130 ```bash
    131 $ go test
    132 $ ls *.v
    133 bmstack_tb.v  bmstack.v
    134 ```
    135 
    136 This example sets up a stack with 5 agents (3 senders and 2 receivers) and then produces the HDL code and the test bench for the stack. The test bench contains a sequence of pushes and pops that are used to verify the correctness of the stack.
    137 In detail the 3 senders push 6 values (2 each) to the stack at different times, while the 2 receivers pop the 6 values (3 each) from the stack at different times. The 6 values are distributed among the 2 receivers.
    138 
    139 ### Example: CLI
    140 
    141 The CLI can be used to produce the HDL code and the test bench for the stack. The following command produces the exact same file (bmsta.v) as the API example above.
    142 
    143 ```bash
    144 $ bmstack -senders sender1,sender2,sender3 -receivers receiver1,receiver2 -hdl-file bmstack.v
    145 ```
    146 
    147 To also produce the (same) test bench, the user can use the following command.
    148 
    149 ```bash
    150 $ bmstack -senders sender1,sender2,sender3 -receivers receiver1,receiver2 -hdl-file bmstack.v -tb-file bmstack_tb.v -stimulus-file stimulus.json
    151 ```
    152 
    153 Where `stimulus.json` is a JSON file that contains the test bench data. The JSON file has the following format.
    154 
    155 ```json
    156 {
    157   "Pops": [
    158     {"Agent": "receiver1","Tick": 110},
    159     {"Agent": "receiver2","Tick": 160},
    160     {"Agent": "receiver1","Tick": 210},
    161     {"Agent": "receiver2","Tick": 260},
    162     {"Agent": "receiver1","Tick": 310},
    163     {"Agent": "receiver2","Tick": 360}
    164   ],
    165   "Pushes": [
    166     {"Agent": "sender1","Tick": 100,"Value": "32'd1"},
    167     {"Agent": "sender2","Tick": 150,"Value": "32'd2"},
    168     {"Agent": "sender3","Tick": 200,"Value": "32'd3"},
    169     {"Agent": "sender1","Tick": 250,"Value": "32'd4"},
    170     {"Agent": "sender2","Tick": 300,"Value": "32'd5"},
    171     {"Agent": "sender3","Tick": 350,"Value": "32'd6"}
    172   ],
    173   "TestSequence": null
    174 }
    175 ```
    176 
    177 The JSON file contains the same data as the test bench data in the API example above. The user can use the JSON file to provide his own test bench data to the CLI. With -random-stimulus the user can also generate random stimulus data for the test bench.
    178 The CLI can be used to produce the HDL code and the test bench for a custom distributed stack/queue to use in other projects.
    179 
    180 `Warning`: If the simulation prints a message like
    181 ```
    182 Warning: impulse while request is active, the impulse will be ignored
    183 ```
    184 
    185 it is due to the fact that the test bench data is not correct. Some pops/pushes are fired while the stack has already a request active from the same agent. In a real scenario, the agent would wait for the ack signal before sending another request.
    186 The test bench provided in the example is correct.

    188 ## Simulation
    189 
    190 Whether the HDL code is produced using the API or the CLI, the user can simulate the stack/queue using the provided test bench. The test bench is written in Verilog and can be simulated using any Verilog simulator. Here we provide an example using the Icarus Verilog simulator to run the simulation. The simulation produces a vcd file that can be viewed using gtkwave.
    191 
    192 Following the API example above, the user can simulate the stack using the following commands.
    193 
    194 ```bash
    195 $ iverilog -o bmstack.vvp *.v
    196 $ vvp bmstack.vvp
    197 VCD info: dumpfile bmstack.vcd opened for output.
    198 stack_tb.v:142: $finish called at 1304000 (1ps)
    199 $ gtkwave bmstack.vcd
    200 ```
    201 
    202 ![Sim](sim.png)
    203 
    204 The simulation shows the stack in action. The stack is filled with 6 values and then the values are popped by the receivers. The values are distributed among the two receivers as expected. Alongside the values pushed and popped, the simulation also shows some internal signals of the stack.

    206 ## Interface
    207 
    208 To use the generated HDL code, the user needs to connect the stack/queue to the agents that send and receive data. The stack/queue has the following interface.
    209 
    210 ### Senders
    211 
    212 The senders need to connect the following signals to the stack/queue.
    213 
    214 - `clk`: The clock signal
    215 - `reset`: The reset signal
    216 - `[sendername]Data`: The data to be pushed to the stack/queue
    217 - `[sendername]Write`: The write signal to push the data to the stack/queue
    218 - `[sendername]Ack`: The acknowledge signal to confirm the data has been pushed to the stack/queue
    219 
    220 So, for example, if the user has a sender agent called sender1, the user needs to write the data to be pushed to the stack/queue in the `sender1Data` signal, then set the `sender1Write` signal to 1 to push the data to the stack/queue. The `sender1Ack` signal will be set to 1 when the data has been pushed to the stack/queue.
    221 
    222 Sendername is the name of the sender agent chosen by the user.
    223 
    224 ### Receivers
    225 
    226 Similarly, the receivers need to connect the following signals to the stack/queue.
    227 
    228 - `clk`: The clock signal
    229 - `reset`: The reset signal
    230 - `[receivername]Data`: The data to be popped from the stack/queue
    231 - `[receivername]Read`: The read signal to pop the data from the stack/queue
    232 - `[receivername]Ack`: The acknowledge signal to confirm the data has been popped from the stack/queue
    233 
    234 So, for example, if the user has a receiver agent called receiver1, the user needs to set the `receiver1Read` signal to 1 to pop the data from the stack/queue. The `receiver1Data` signal will contain the data popped from the stack/queue. The `receiver1Ack` signal will be set to 1 when the data has been popped from the stack/queue and is available in the `receiver1Data` signal.
